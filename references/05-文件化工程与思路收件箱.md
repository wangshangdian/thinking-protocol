# 05 · 文件化工程与思路收件箱

> 铁律：**子任务不靠「记忆」传递，靠「文件」传递。**
> 模型不"记住"，只"读到"。所以：哲学必须写下来，并且每次开工都被读到。

## 一、文档骨架

```
docs/
  00-项目章程.md          宪法层：目标 / 边界 / 底层思维。单一事实源，少改，改要记日期
  01-思路评估.md          成熟想法逐条裁定（判定 + 去向 + 前置条件 + 否决条件）
  02-子任务登记.md         状态机 + 结论摘要
  03-思路收件箱.md         ⭐ 新想法先丢这里，追加式，不打断主线
  04-轮子清单.md          先找轮子
  05-方法论与教训.md       复利资产：M 编号通则 + 坑编号
  06+ 编号递增-主题.md      领域文件（06 数据体系 / 07 领域A / 08 领域B …）
  子任务/SC-XX-短名.md      自包含开工包（6 段）
```

一键生成：`scripts/init_project_docs.py <项目根目录>`

**编号规则：只增不减。** 作废的课题是资产（它告诉你此路不通），写明为什么废，不要删除。

## 二、思路收件箱协议（防打断上下文）

**收件箱的唯一职责：让人随时丢想法，不被打断，不用组织语言。**

写入格式（最简）：
```
- [ ] 2026-09-18 · <一句话想法>
      补充（可选）：<为什么 / 什么场景下想到的>
```

**处理时做三件事**（AI 负责，用户不参与分诊）：

1. **分诊**：
   - 已成熟、可直接评价 → `01-思路评估.md`
   - 需要独立研究 → `02-子任务登记.md` 开子任务（`SC-XX`）
   - 太小 / 太远 → 先攒着，不处理
2. **更新去向**：在对应文件里建立/更新条目
3. **勾选**：收件箱条目改为 `[x]`，标注去向

**每次开工先读收件箱。** 这是唯一能保证"想法不会丢"的动作。

## 三、回写三处（防「钱白花」）

研究做完，**必须**回写三处，缺一不可：

| 回写到哪 | 写什么 |
|---|---|
| `docs/02-子任务登记.md` | 该行状态改为 `已闭环` + 3 行内结论摘要 |
| `docs/子任务/SC-XX-短名.md` | 追加 `## 结论` 段 + 产出物路径 |
| `docs/05-方法论与教训.md` | **若**发现了可复用的思维模式或新踩的坑，加一条 |

> 为什么强调：新对话的上下文**会消失**，文件不会。不回写 = 这次研究的成本白花。

## 四、自包含开工包（6 段）

判断：「这件事做完，我们还会不会继续改它？」会 → 开独立课题；不会，一次成型 → 当场做。

每个独立课题在 `docs/子任务/SC-XX-短名.md` 里放一份**自包含**开工包。
"自包含"的标准：**新对话完全不看本项目其他文件，也能开工。**

| 段 | 内容 |
|---|---|
| 1. 背景 | 3 行以内，让新对话知道这是谁的、为什么做 |
| 2. 要解决的问题 | 一句话 |
| 3. 期望产出 | 具体产物形态（脚本 / 数据集 / 报告） |
| 4. 已知轮子 | 先找轮子，避免重复造 |
| 5. 已知坑 | 已踩过 / 已核实过的，别重复踩 |
| 6. ★ 复制区 | 一段可直接粘贴到新对话的 prompt（含协作契约短锚） |

## 五、状态机

                    └── 发现前提错误 ──▶ ⛔作废（写清为什么废，不删）

## 六、多会话如何继承（「我开多个对话」的答案）

五层防线，从弱到强：

| 层 | 载体 | 何时生效 | 可靠性 |
|---|---|---|---|
| 1 | `docs/00-项目章程.md` §底层思维 | 被读到时 | 依赖读到 |
| 2 | `docs/10-AI协作契约.md`（自检清单 + 可粘贴短锚） | 被读到时 | 依赖读到 |
| 3 | 开工包「★ 复制区」 | 用户粘贴时 | 依赖粘贴 |
| 4 | **技能**（skill） | 提到关键词时自动触发 | 可能漏触发 |
| 5 | **UserPromptSubmit hook** | 每次提交消息必触发 | **100%，不依赖任何人** |

**结论**：
- 想"开新对话就自动继承"→ 用**用户级技能**或 **hook**（不依赖记忆和自觉）。
- 想"跨项目复用"→ 用**用户级技能**（放在用户目录，所有工作空间可见）。
- 想"保证 100% 生效"→ 只有 **hook** 做得到；技能会漏触发。
- 短锚是"离开工作空间 / hook 失效"时的**备份**手段。

⚠️ **贯穿一切的唯一铁律 —— 单一事实源**：
哲学 / 规格条文**只**写在一处（章程）。其他层只能"引用 + 执行"，**绝不复述条文**。
两边都写 = 将来必定打架。

## 八、版本控制 —— 文件化的底座（2026-09-18 实证补入）

**核心判断：把「云同步」当「版本控制」是一个会导致静默数据丢失的假设。**

| | 云同步（OneDrive / iCloud / 坚果云） | 版本控制（git） |
|---|---|---|
| 设计目标 | **多端保持一致** | **保留每一次变更的历史** |
| 冲突时 | 生成 `文件名-计算机名.ext` **副本**，让你自己收拾 | 三方合并 / 冲突标记 |
| 能否回答"昨天这行是什么" | 基本不能（消费级版本历史极短） | 能：`git log -p` |
| 回滚颗粒度 | 整个文件 | 一行 |
| 能否发现"1 个坏字节" | **不能** | 能：`git diff` 整行变色 |

### 实测过的三种静默损坏（都不报错、文件都能照常打开）

1. **主文件丢整节内容，内容只活在冲突副本里**。同一项目里发生过**两次**
   （一份方法论文件的整节、一份清单的一行）。用肉眼看主文件完全正常。
2. **1 个非法 UTF-8 字节**。严格解码失败；用 `errors='replace'` 读只看到一个 `�`。
3. **编号冲突**：两份文件给同一编号分配了不同主题（如两边都有 `M29`，指向不同结论）
   ⇒ 读者按编号去找会找到错的东西。抢救内容时**必须顺便重新编号**。

### 两条底线

1. **建库 + 基线提交，然后才允许删改。** 删错/改错的后悔药 =
   `git checkout <基线sha> -- <路径>`。**没有基线提交就不做删除动作。**
2. **每次实质改动后，`git log --oneline` 要能看见它。**

### 冲突副本处理清单（按顺序，不要跳）

1. 🚨 **绝不直接删**。
2. **比对内容**——用行级集合差，别肉眼扫（本次就是"看起来是旧副本"的那个文件里藏着独有的整节）。
3. 抢救独有内容进主文件，**并解决编号冲突**。
4. **提交**，然后才删副本。
5. 追问根因：**为什么会同时存在两套？**
   若两台机/两个设备**主机名相同**，冲突副本会**同名互覆** ⇒
   副本数量与实际冲突次数不成比例、谁赢谁输不可预测。**先改名，再谈整理。**
