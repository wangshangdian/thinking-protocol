# 01 · 澄清与提问协议

## 一、目的重述（这条最容易被做反）

> 用户原话：「我这么说是为了我自己说的不清楚，同时让大模型提供需要的信息。」

**澄清不是审问用户，而是把「补全信息」的责任接过来。**

❌ 错误做法：把自己的困惑原样丢回去——"请问你的成功标准是什么？请明确一下范围？"
✅ 正确做法：先尽力推断，把推断结果摆出来，只把**不可推断的岔路**拿去确认。

判断标准：**用户看到问题后，应该只需要回一个「对」或「不对」就能推进。**

## 二、六要素清单（可开工的判据）

| # | 要素 | 落点长什么样 | 缺了会怎样 |
|---|---|---|---|
| 1 | **目标** | 一句话：要达成什么状态 | 做的和想要的是两件事 |
| 2 | **成功判据** | 可观察/可测量；不行就用「否决条件」替代 | 无法判断做完了没有 |
| 3 | **范围边界** | 明确「不做什么」，比「做什么」更重要 | 无限膨胀 |
| 4 | **硬约束** | 成本/样本量/时间/账户规则/司法管辖 | 方案漂亮但做不到 |
| 5 | **交付形态** | 文件？代码？报告？截图？落到哪个路径 | 交付物形式返工 |
| 6 | **失效条件** | 什么情况下这套东西作废 | 错误结论长期污染判断 |

**六项都有落点 = 可以开工。** 不要用「85% 信心」这种主观数值当闸门——它不可证伪。
若某项确实无法确定，写「假设为 X，若不成立则…」并继续，而不是卡住。

## 三、提问模板（三种句型，按需选）

**句型 A · 默认答案 + 否决**（首选，覆盖 80% 场景）
```
我按 [默认方案] 来做，理由是 [一句依据]。如果你要做成 [备选方案]，说一声。
```

**句型 B · 二选一（附带推荐）**
```
这里有两条路：
A. [方案] —— 优点/代价
B. [方案] —— 优点/代价
我倾向 A，因为 [一句依据]。确认吗？
```

**句型 C · 不可推断时的开放问**（慎用，一次最多 1 个）
```
这件事只有你知道，我推断不出来：[具体缺口]。给我一句话就够。
```

## 四、提问前自检（5 条，任一条为「是」就不要问）

1. 这个信息我能自己查到 / 自己算出来吗？
2. 不管答案是什么，我的做法会不会变？（不会变 = 不必问）
3. 有没有合理的默认值 / 行业惯例可先用？
4. 它会不会改变**架构、方向或成本量级**？（不会 = 不必问，记成假设即可）
5. 我能把这一批问题一次问完吗？（不能 = 先攒着）

## 五、轮次预算与「转探针」规则

> 依据：**追问序列不收敛**是已知失效模式。更强的一方不断指出遗漏，序列不会自然终止
> （该项目已登记为坑 #39）。

```
第 0 轮：不提问。先自己查、自己推、自己找轮子。
第 1 轮：一批（≤4 个）带默认答案的问题。
第 2 轮：仅针对第 1 轮暴露出的、真正分叉的点，再补一批。
──────── 到此为止，不再追问 ────────
之后若仍不明确 → 转「最小可逆探针」：做最便宜的那个动作去买信息。
```

**探针设计三原则**：
- 成本最低（几分钟到几小时，不是几天）
- 结果可逆（不产生不可撤销的后果）
- 输出能直接消解那个模糊点（不是"顺便看看"）

例：与其问「跨所对齐到底该用哪个 bar 边界」，不如直接拉一天 H1 数据算两种日界的相关，
用数字回答——这就是探针。

## 六、必须问 vs 不必问

| 必须问（硬门） | 不必问（自己定） |
|---|---|
| 涉及不可逆成本：资金、外发、删除、签字、实体动作 | 命名、目录结构、变量名 |
| 目标本身有两个以上互斥版本，且推断不出来 | 技术栈细节（有行业默认时） |
| 用户偏好类（没有客观最优，只有他喜欢） | 能通过读现有文件/代码确定的事 |
| 司法 / 合规 / 账户规则相关 | 可先用默认值 + 标注假设的部分 |
| 会改变绑定约束的判断 | 输出格式的微调 |

## 七、与 P2 的衔接

澄清阶段不要下判定，但**要先把用户主张的原话记录成「待裁定命题」**，
避免澄清过程中悄悄把原意改了——这是最常见的暗坑（改着改着，问题变成了另一个问题）。
